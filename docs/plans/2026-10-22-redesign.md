# Charter redesign plan

**Date:** 2026-10-22
**Status:** ruled; all §9 decisions recorded as D1–D11 in `docs/meetings/`. Amended 2026-10-23 at Eric's direction: the compiler/server split (§3a, §4, §5.5, §6, Phase 3 reordered, Phase 3b added); D12 delegated; B9 and B10 open.
**Supersedes:** the v0.3 layout described in `README.md`, `HANDOFF.md`, and `docs/charter-spec.md`

## 0. The brief, and what is already decided

The brief, in Eric's words:

1. Charter should be a real language.
2. Borrow the good parts of With's development and design process.
3. Mainly inspired by eFLINT.
4. Lean is the engine, but Charter developers should not have to look at, experience, or know Lean.
5. Learn from the best parts of the four reference repositories (`.reference/eflint`, `catala`, `quint`, `symboleo`): semantics, compiler architecture, build process, repository structure.

Ruled on 2026-10-22, recorded as D1–D3 in `docs/meetings/`:

- **D1. Lean-hosted compiler, Lean-free output.** The `charter` binary is written in Lean and ships as one native executable. It parses, checks, evaluates, simulates, and projects `.charter` programs itself. Lean proofs certify the compiler and semantics once, at Charter's own build. Users install one binary. Lean never appears in a diagnostic. Per-program kernel proofs are an opt-in `charter prove` that drives a Lean toolchain the binary manages, the way With carries Clang.
- **D2. Every eFLINT program is a Charter program.** eFLINT's constructs, keywords, phrase language, and semantics are Charter's core, extended rather than replaced. The eFLINT test suite and examples corpus are Charter regression tests.
- **D3. The PSA is rewritten in Charter.** Lean remains only for what the language cannot say, and that remainder is expected to shrink release over release.

## 1. Goals and non-goals

The goals are `docs/mission.md` and are not restated here. Three consequences of their order of precedence shape this plan:

- Goal 1 is the yardstick for every phase. A phase that does not let more of the Protocol of Sovereign Agency be written in Charter is not a phase of this plan; the PSA is not a late milestone (§8).
- Goal 1's sentence "the protocol amends itself under its own rules" means parameters and rules are state the program's own acts can change, not configurations supplied from outside (§2.2.8).
- Goal 3 makes the contract guard and the agreement text release targets with their own acceptance scenarios, not demonstrations (§6, §8). Amended 2026-10-23 (§3a): the three readings are one *artifact* in three hosts, not three projections. The document is in the artifact; the guard and the server both run the proved evaluator against it; the briefing is the server answering from it. The only faithfulness proof is the evaluator's, done once.

**Non-goals for v1.** Dates and calendars beyond integer time. Floating point. Multi-language keywords. A web IDE. Replacing eFLINT's TCP server protocol (we expose JSON over stdio first). Self-hosting.

## 2. The language

### 2.1 From eFLINT, kept as-is

Everything below keeps eFLINT's spelling and meaning so that D2 is literal. Source: `.reference/eflint/src/Language/EFLINT/{Parse,Spec,StaticEval,Eval,Interpreter}.hs` and the survey in the session of 2026-10-22.

| Construct | Kept |
|---|---|
| `Fact name [Identified by TYPE] [Where e]` with `String`, `Int`, `Time`, enumerations, products `a * b`, `Open`/`Closed`, `Var`, `Function`, `Bool`, `Placeholder x For t` | yes |
| `Holds when` (derivation over the enumerable domain), `Derived from` (generation), `Conditioned by` (precondition filter) | yes, including the three different roles |
| `Act name [Actor v] [Recipient v] [Related to …]` with `Creates`, `Terminates`, `Obfuscates`, `Syncs with`, `When` guards on effects, `Foreach` | yes |
| `Physical`, `Event` | yes |
| `Duty name Holder v Claimant v [Related to …]` with `Violated when`, `Enforced by`, `Terminated by`, `Created by` | yes, with the same desugaring |
| `Predicate`, `Invariant` | yes |
| `Extend` | yes |
| Expressions: `&& \|\| !`, comparisons, arithmetic, `Sum/Count/Max/Min`, `Exists/Forall`, `When`, `Holds()`, `Enabled()`, `Violated()`, projection `e.f`, named arguments `f(x = e)`, free-variable binding (`Exists` in conditions, `Foreach` in effects) | yes |
| Phrases: `+e`, `-e`, `~e`, `a(args)`, `?e`, `?!e`, `?- e`, `?-- e`, `{ … }` parallel blocks, `#include`, `#require`, `.` terminator | yes |
| Semantics: closed types default false, open types raise missing input, create beats terminate within a step, saturation after every phrase, violations reported per phrase | yes |

Known eFLINT defects we fix rather than reproduce, each under a decision naming the defect and the tolerance (D2): derivation is an unstratified naive fixpoint whose result can depend on type order (D6: stratify, reject unstratifiable negation); `Current Time` never advances (D7: time is implemented, §2.2.3); duties are re-reported while they stay violated (we report on transition, as their TODO asks; decision pending); duplicate declarations silently replace (we error; decision pending).

### 2.2 Charter's additions

These are the reasons Charter exists. Each is a new keyword or clause, never a change to an eFLINT meaning.

1. **Validity separate from permission** (D5). An `Act` gains `Valid when e`. `Holds when` says whether performing the act is *lawful* (eFLINT's meaning); `Valid when` says whether it has *institutional effect*. Effects apply iff valid. A disabled act is a violation either way. An act with no `Valid when` is valid always, so an eFLINT program behaves exactly as in eFLINT: effects apply even when disabled. This is the one place Charter's seven commitments and eFLINT's model differ, and the default keeps compatibility.
2. **Immunity.** `Immunity name Holder v Against a1, a2 [Holds when e] [Unless e]`. While it holds, the named acts are not valid against the holder. A separate construct, not a `Conditioned by`, so that the precedence edge from protection to power is data the projections and views can show.
3. **Time.** `Current Time` advances. Every fact instance carries the time it was established and an optional expiry (Law 7); time is state, and nothing in a trace is a "lapse event". The phrases `@ t.` and `tick.` are environment input (Law 6) that set the clock, not acts any party performed, and they do not appear in the event history. New conditions `held for d` (`Holds(e) Since d`), `count(e) >= n`. New effects `Creates e For d` (expiry stamp). New duty clause `Due within d` (a requirement duty, breached when `d` passes after creation without the terminating act). `Time` (instants) and `Duration` (differences) are distinct types over `Int` (D7): `Time + Duration : Time`, `Time - Time : Duration`, no `Time + Time`; a literal coerces to either by demand; `held for`, `For`, and `Due within` take a `Duration`, and a `Param` may be declared `: Duration`. Calendars are a later chapter and an extension, not a migration.
4. **Authority exceptions.** `Act x … Except under a1, a2`: performing `x` is lawful when and only when it is also a valid exercise of one of the named acts. This is Charter's `unlessPower`, which eFLINT can only write as a disjunction in `Holds when`.
5. **Clauses and provenance** (D4: files are code-first; a literate `.charter.md` container lowering to the same `Doc` arrives in Phase 5). `Clause ID [Approved HASH]` with `Text "…"` and register spans `Norm "…" => ids`, `Definition`, `Invariant`, `Acceptance`, `Commentary`; `Document "path"`. Every Act, Duty, Immunity, and Invariant may carry `From CLAUSE "span"`. Checks: spans reproduce the clause, every norm span names a rule, every rule is named by a span, the clause text occurs verbatim in the document, the approved hash matches. Unchanged from v0.3, now with the hash printed by `check` and invariant spans required to name a declared `Invariant`.
6. **Scenarios and expectations in the file.** `Scenario name { phrases }` groups phrases as a named test. New expectation phrases: `?lawful a(args)`, `?valid a(args)`, `?violated d`, plus eFLINT's `?`/`?!`. `charter test` runs every scenario; `charter run` runs the top-level phrases.
7. **Invariants are checked, not just declared.** An `Invariant` is checked after every phrase (eFLINT) and, by `charter test --explore`, by bounded search over acts from the scenario's end state, reporting the shortest violating trace with a seed (Quint). `charter prove` turns a named invariant into a Lean theorem obligation over all traces of the lowered law.
8. **Parameters are facts; amendments are acts; ratchets are immunities** (D11). `Param name = n` declares a `Var` fact over `Int` whose initial instance is `n`; any `Int` position may name it. An act may `Creates noticeWindow(20)`, and the program judges that amendment like any event. Rule amendment is the act `Amend`, whose `Creates`/`Terminates` target rule records (a duty, a power, an immunity, a clause binding), so every rule change has an actor, a stamp, a validity answer, and an effect answer, and "what were the rules when X happened" is answered from the trace. Entrenchment is `Immunity I.NAME Holder … Against Amend` naming the rule records it covers; it covers itself and whatever governs `Amend`'s validity (reflexive), so a weakening `Amend` is performed, recorded, and void. Consent and timelocks are `Valid when` facts. `Extend` stays eFLINT's scenario-time mechanism and is never a run-time rule change. `Regime "label" { name = n }` is an alternative initial state for `charter explore`, nothing more. `charter diff` compares the rule set before and after each `Amend` and reports which protections voided it. The universal ratchet theorem becomes: every valid `Amend` trajectory preserves every `Invariant` tagged `Entrenched`, proved from the fact that no effective weakening occurs.
9. **Modules** (D8). `#require` stays for files. `Module name(params) { declarations }` and `Use name(args) As prefix` instantiate a declaration block with substitution, the way Quint imports instances. The eight standard-library patterns are shipped as `.charter` modules under `lib/`; every property is an `Invariant` in the module file, proved in `lib/lean/Modules/` by that name and reported as *proved* when a program `Use`s the module.
10. **Individuals and roles together.** eFLINT already has individuals (`Fact person Identified by Alice, Bob`). Charter adds nothing here except that `Actor`, `Holder`, `Claimant`, and `Recipient` are statically checked to be actor types (their TODO).
11. **Every fact knows where it came from** (Law 6). The state records, per instance, whether it was asserted by a phrase, supplied by the environment (`Open` input, `@ t`), created by a named act at a time, or derived by a named rule. The phrase `?why e` and the command `charter why <fact>` print that chain. No evaluator path creates a fact without an origin.
12. **Every answer says which question it answers** (Laws 2 and 10). A transition report labels each judgment *occurred*, *lawful*, *valid*; each is reported even when the others are not. Every claim the tool prints, from `check` through `prove`, carries exactly one of the tags *proved*, *decided*, *checked*, *assumed*; the tag is part of the diagnostic record (§3), not prose.

### 2.3 What leaves

- The `charter_*` Lean macros (`Charter/Surface/Syntax.lean`): two spellings of one meaning (Law 13). Removed in Phase 4 once the PSA and commons are `.charter` files whose Lean companions import the lowered law.
- `Unlower.lean` and `charter export`: a one-time migration tool. Removed after the last export.
- The v0.3 flat `duty`/`power` grammar: superseded by §2.1 and §2.2. The exporter emits the new grammar during migration.
- `Charter/Substrate/*` as models the evaluator runs (D10): affiliation, control, sortition draws, and valuations become environment facts (`Open` inputs); their properties become named `SUB.*` assumptions a program cites, tagged *assumed*, with the existing Lean theorems kept under `lib/lean/` only as proofs of those assumptions' consistency.
- Scenario JSON files: scenarios live in `.charter` files. The CLI keeps reading JSON until the PSA scenarios are moved.
- `RatchetSpec` and `psaCandidateRegimes` as Lean objects: ratchets become `Immunity … Against Amend` plus `Entrenched` invariants (D11); regimes become initial states in the program.

## 3. Compiler architecture

One Lean package, one binary, a pipeline with a directory per stage and a `from_<prev>` module in each (Catala), every stage dumpable as JSON (Quint `--out`), one evaluator that is the proved artifact.

```
Surface   .charter text ──lex──▶ tokens ──parse──▶ Surface.Ast     (positions on every node)
Resolved  names, types, arities, actor checks, module instantiation, #require ──▶ Resolved.Ast
Core      Charter.Core.Law σ_dyn + Clauses + Params + Scenarios       (the semantics object)
Eval      saturation, triggers, violations, time                      (proved against Core semantics)
Artifact  Core law + document + proof certificate, under one hash     (what the compiler produces; §3a)
Project   views, explain, prompt, abi, veil, diff, timeline           (read the artifact's records)
Prove     Lean source generator + toolchain driver                    (opt-in; its output is the certificate)
```

Phase 1 note (2026-10-23): for the eFLINT core, `Resolve` is eFLINT's static evaluation (names, types, arities, the rewriting of conditions into their checked form) and its output *is* the Core object, a `Spec` of `TypeSpec` records (`src/Charter/Core/Spec.lean`); a separate `Lower` stage appears in Phase 2 when Charter's additions need a resolved AST distinct from the records.

Rules (D1, D9, D11; the rest are recorded as they land):

- **The rule set is state.** Because `Amend` targets rule records (D11), `Core.Law` is part of the evaluator's state, addressable by rule id, and the trace determines the rules in force at every step. Immunities name rule ids in `Against`.
- **The evaluator is the semantics.** `Charter.Eval` is defined in Lean, proved to agree with `Charter.Core.Semantics` (occurrence, compliance, validity, derivation fixpoint), and compiled into the binary. There is no second interpreter. Quint's two evaluators and Catala's interpreter-at-two-IRs are the anti-pattern here.
- **Diagnostics and claims are data.** Every error and warning is `{code: "CHR###", severity, message, span: {file, start, end}, notes}`; every claim (a check result, a scenario expectation, a theorem outcome) is `{claim, tag: proved|decided|checked|assumed, about: occurred|lawful|valid|…, span}`; the CLI renders them, the LSP forwards them, tests pin them. Codes are allocated in `docs/spec/diagnostics.md` and never reused (Quint ADR002). Parse errors have hand-written messages per state where the parser allows it (Catala `parser.messages`).
- **Keep going after errors.** Resolution continues past the first error to report more, as Quint does; evaluation does not run on an erroneous program.
- **`charter prove` is a generator, not a mode** (D9). It writes a Lean project into `.charter/prove/<program>/` containing `charter_program "…"` plus one theorem per named invariant and expectation, runs the toolchain the binary fetches by digest into `~/.charter/toolchains/<digest>/` on first use (`--offline` refuses rather than searching PATH), and reports per-theorem results through the same diagnostic channel. Users see theorem names and pass/fail, never Lean output, unless they pass `--show-lean`.
- **The LSP is the library.** `charter lsp` links the same stages; hover shows the rule's English span and its lowered form; go-to-definition works across `#require`.

### 3a. Two tools, two audiences, one artifact (added 2026-10-23)

eFLINT ships a server (`.reference/eflint/src/Server.hs`) that loads *source* and compiles it at run time: whoever operates it sees the program, and nothing it answers can be replayed without trusting the operator's copy. Charter splits the two roles.

| | Compiler (`charter`) | Server (`charter-server`) |
|---|---|---|
| Input | Charter source | an artifact, a history, events |
| Output | the artifact: compiled law, proof certificate, span-checked document, under one hash | the three answers per event; the appended history |
| Who uses it | developers | agents, hosts, settlement layers, arbiters |
| Trusts | the kernel | the certificate checker, then nothing |
| Changes when | the source changes | never, for a given artifact |

- **The compiler is the developer's tool.** Write, check, test the adversarial scenarios, prove, render the document, see every diagnostic in Charter's terms (Law 11). Developers never touch a running institution; they produce the thing one runs.
- **The server is the runtime's tool.** It loads an artifact, verifies its certificate once, and then does four things only: accept events, consult the evaluator, append to the history, keep time and leases. It never sees source: its binary contains no parser and no resolver (`operator-blind` gate, §5.5). Its correctness claim is small: it evaluates the artifact it was handed with the evaluator that was proved once.
- **Replay is the trust model.** Anyone who distrusts a server replays the history through their own copy with the same artifact hash and gets byte-identical answers (`replay` gate). A compromised compiler can at worst emit an artifact whose certificate fails.
- **Amendment crosses the boundary once.** A valid `Amend` act's effect is a new artifact (D11). The server does not compile; it checks. A party produces the proposed artifact with the compiler and submits it as the `Amend` act's payload; the server judges the act under the current law (consent, timelock, immunities) and verifies the new artifact's certificate against the entrenched invariants; if both pass, the new artifact takes office at the stamped time (`certificate-at-office` gate). Only the certificate checker lives in the server, and it must be small enough to (B10: who signs the certificate and what the server checks it against is an open decision; it blocks the artifact format, not Phases 1–2).
- **Consequences for the mission text**, drafted here for Eric's blessing (normative wording is his; nothing in `docs/mission.md` is edited by this plan): (i) goal 3 is restated as one artifact in three hosts, which removes per-projection soundness theorems from Law 14's gates; (ii) a purpose sentence, since the mission says what Charter is and not what it is for: the reader of a Charter program is an agent that must act under it, which is what justifies goal 1 and Law 11; (iii) an operator law beside Law 11: the operator never sees source, and any two servers given the same artifact hash and history produce identical answers; (iv) an amendment law naming what D11 introduced and no law yet says: amendment is an act in the history, entrenchment is reflexive, and a new law takes office only with a checked certificate; (v) Law 10's *checked* tag sharpened to "by the proved evaluator over a certified artifact at run time", which is what every server answer is, stronger than an unproved run-time check and weaker than *proved*.

## 5. Process, borrowed from With

### 5.1 `docs/mission.md`

Written 2026-10-22 from Eric's statement of the mission: (1) fully formally represent the Protocol of Sovereign Agency; (2) be a universal language for any such law or contract; (3) be one language for human contracts, smart contracts, and law, each a proved projection of the same program. The fourteen laws are in that file with their test questions. Two consequences for this plan: mission goal 1 makes §2.2's quantities, individuals, and time non-negotiable for Phase 4, since the PSA cannot be "fully" represented without them; mission goal 3 promotes `Project/ContractABI` from a demonstration to a release target with its own UAT (deploy the generated guard to a local EVM and drive a scenario through it).

### 5.2 Decision log

`docs/meetings/README.md` index, newest first, titles that state the rule. One file per decision: `YYYY-MM-DD-D<N>-<slug>.md` with `**Laws:**`, `**Date:**`, `**Status:**`, Ruling, Context, Alternatives, What the references do (eFLINT, Catala, Quint, Symboleo, checked in `.reference/`), Mission fit, Cost accepted, **Reopens if**. ### 5.4 Test battery and tiers

- **Fixture format.** A test is a `.charter` file whose expected result is inline in a trailing comment block, in With's directive style: `//! expect-transition: +fact, -fact, violated duty …`, `//! expect-error: CHR042 line 7`, `//! expect-query: pass`, `//! known-issue: #NN why`. One command, `charter test-battery --reset <file>`, fills expectations; `git diff` is the review (Catala `clerk test --reset`). `known-issue` fails if the test unexpectedly passes (With D23).
- **The eFLINT corpus** is vendored unchanged under `test/eflint-corpus/` and run in `--eflint` mode, where the only accepted differences are the four fixed defects in §2.1, each listed in a tolerance file with its decision number.
- **Tiers** (With D131): *fix* = `lake build` plus touched fixtures; *PR* = `tools/battery` (all fixtures, corpus, spec conformance, gates, UAT); *release* = PR tier plus projections goldens, `charter prove` on both examples, and the examples dashboard regenerated with `git diff --exit-code`.
- **CI is not a signal** (With D56): workflows run nightly or on dispatch; a PR is a draft until the battery is green on the maintainer machine with the pinned toolchain, and the green is keyed to tree hash plus toolchain digest.
- **Pins.** `lean-toolchain` is the seed; `tools/pins.lock` records the toolchain and the `charter prove` toolchain digest per platform with a comment history of every bump.

### 5.5 Gates (Law 14)

Under `test/gates/`, one program per law, each written to fail if the law is lost: a scenario in which a forbidden act occurs and is valid (Laws 1, 2); a program where a panel act creates a finding without any `Violated()` (3); a fixture per exception kind that must lower to the matching field and no other (4); every projection built from a `Law` whose rule bodies are opaque constants must still render (5); a program whose only non-derived facts were asserted, with the provenance query answering for each (6); a trace containing no lapse events in which a deadline passes (7); a rule with no span must warn, a drifted clause must report STALE with the new hash (8); the evaluator-agreement theorems build (9); `#print axioms` on every decided scenario is empty and the `sorry`/`native_decide`/`axiom` grep is empty (10); a grep of the shipped binary's strings for `Lean`, `Lake`, `sorry`, `tactic` (11); the corpus run (12); the leak grep of `src/` for any example name and the duplicate-spelling grep (13). From D10: `goal1-no-shadow-model` (no Lean module outside semantics, evaluator, and projection proofs declares anything named for or spanned to a protocol clause) and `psa-adversarial-tests` (one scenario per test in the protocol's Adversarial Tests section, counts equal, spans not drifted). From D11: `amend-is-an-act`, `amend-reflexive`, `extend-never-at-runtime`. From §3a: `replay` (two server processes, the same artifact and history, byte-identical answers), `certificate-at-office` (no artifact takes office in a server without a verified certificate, and a tampered artifact is refused with its hash named), and `operator-blind` (the `charter-server` binary links no module of `Surface/` or `Resolve/`, checked on the module import graph, and its strings contain no keyword of the grammar). Under §3a, gate 5 ("every projection built from an opaque `Law` must still render") stays, and gate 9 loses its per-projection soundness theorems: the one agreement proof is the evaluator's.

### 5.6 Agent rules (`AGENTS.md`)

Written 2026-10-23; `CLAUDE.md` points to it and holds no rules of its own. Carried over from With where they apply, translated to Charter's terms: we own every bug, nothing is pre-existing without verification on the previous commit in a worktree; no stubs, no silent fallbacks, no weakened checks, no edited fixtures; done requires evidence; delete the old route; the spec leads and only Eric blesses normative wording; briefs follow the four-part procedure (what the references do, what the spec says, mission fit, prediction with confidence); record decisions; one logical change per commit; every change via PR, draft until the battery is green (suspended 2026-10-23: pushes go straight to `main` for now, battery still the gate). Charter-specific additions: never introduce a user-visible Lean term; never make a scenario pass by editing the clause text; an eFLINT corpus failure is a semantics bug until proved otherwise.

### 5.7 `handoff.md`

## 6. Toolchain and CLI

One binary. Subcommands, in groups:

| Group | Commands |
|---|---|
| Project | `init` (scaffolds a program, a document, a scenario, and `uat/hello.uat`), `fmt`, `lsp`, `doc` |
| Check and run | `check` (parse, resolve, provenance, staleness), `run [file]` (top-level phrases, prints labelled transitions), `test` (scenarios; `--explore` bounded search; `--seed`), `repl`, `why <fact>` |
| Prove | `prove [--invariant name] [--show-lean]` |
| Projections | `render` (the agreement as people sign it: the document with each clause's rules beside it; goal 3's first reading), `prompt [actor]` (goal 3's third), `abi` (goal 3's second, with a UAT that deploys the guard to a local EVM and drives a scenario through it), `views`, `explain <who> <act>`, `veil`, `diff`, `explore`, `trace <clause>` |
| Interop | `import x.eflint` (rewrites to Charter spelling, identity on the common subset), `--out json` on every stage, `--itf` traces from `test` and `run` |
| Artifact | `build` (source to artifact: law, certificate, document, one hash; `prove` fills the certificate), `inspect <artifact>` (the records, never source) |
| Info | `version`, `help` |

`init` writes a UAT scenario so acceptance testing is a feature every program has (With D67). JSON output everywhere (Quint): `check --out`, `test --out`, diagnostics as a stream.

The second binary, `charter-server` (§3a), has its own small surface: `serve <artifact> [--history <file>]` (verify the certificate, load, then accept events over JSON on stdio and answer each with its three labelled judgments, appending to the history), `replay <artifact> <history>` (recompute every answer; the `replay` gate diffs two runs), and `verify <artifact>` (the certificate check alone). It has no `check`, `run`, or `test`: those need source, and the server never sees source.

## 8. Phases and exit criteria

No dates. Each phase ends when its gate passes.

**Phase 0, process scaffolding.** `docs/mission.md`, `docs/meetings/` with D1–D3 and the backfill, `docs/spec/README.md` skeleton with the chapter list, `CLAUDE.md`, `handoff.md`, `test/gates/` with the trust and leak greps, `tools/battery`. *Exit:* battery runs green on the current code; every decision made this month is recorded.

**Phase 1, the eFLINT core.** Lexer, parser, resolver, lowering, and evaluator for §2.1; `check`, `run`, `test`, `repl`; diagnostics with codes; the vendored eFLINT corpus passing in `--eflint` mode with only the four tolerated differences; the evaluator's agreement proof with `Core.Semantics` for derivation, triggers, and violations. *Exit:* corpus green; `test/spec` for chapters 002–011 written and green; no `sorry`.

**Phase 2, Charter's additions.** `Valid when`, `Immunity`, `Except under`, time, clauses and provenance, `Scenario` and expectations, checked `Invariant`, parameters as facts, `Module`/`Use`, `?why`, labelled transitions and claim tags, the eight `lib/` modules as `.charter` with their theorems reattached, and a first `prove` (the generator; until the managed toolchain lands in Phase 4 it is a maintainer tool run with the repository's own `lean-toolchain`, not shipped to authors, so D9 is not yet in force). *Exit:* the tenancy example exercises every addition; spec chapters 005–015 green; `commons` rewritten and its eight simulations reproduced by `charter test`; PSA Law 3 (non-interference and adjudicated suspension, 15 clauses) written in Charter with its invariants INV.8 and INV.9 discharged by `prove`.

**Phase 3, the Protocol of Sovereign Agency.** Reordered 2026-10-23 (§3a): first the artifact format (`src/Charter/Artifact/`: the Core law, the document with its spans, the proof certificate, one hash over all three), since every later step is defined against it and B10 must be ruled before it is fixed; then `Amend` with the certificate check at office; then the rest. The whole PSA per §7: all 61 clauses, every party as an individual, every quantity as an `Int` fact, every deadline over time stamps, every amendment as an act, scenarios in the file replacing `scenarios/*.json`, `Invariant` declarations for INV.1–14 whose `From` spans are the 14 invariant spans. Every one of the 16 adversarial tests becomes a scenario naming its span; a test the evaluator cannot run is filed as a language feature request before the phase ends and is implemented or the protocol's English is amended (D10, never a retained Lean model). `Amend` and reflexive entrenchment land here (D11) with Law 7 of the protocol as the test. Then the deletions: `ProtocolWorldState` and the Lean simulations, `charter_*` macros, `Unlower`, the v0.3 grammar, the JSON scenario files. *Exit:* `charter prove examples/sovereign_agency` discharges INV.1–14; all 16 adversarial scenarios pass with their tags; the `goal1-no-shadow-model` and `psa-adversarial-tests` gates pass; nothing of the protocol lives only in Lean or only in prose (goal 1); the Law 13 grep finds no second spelling.

**Phase 3b, the server** (added 2026-10-23; §3a). `charter-server`: load an artifact, verify its certificate, evaluate events with the same `Charter.Eval` the compiler links, append to a history, replay a history. Built against the artifact format as soon as it exists in Phase 3, so the format is exercised by both consumers before the compiler's projections are finished. B7's residue gets its sharper test here: every one of the protocol's 16 adversarial scenarios runs through the server, since that is the evaluator that will judge real agents, and running through the compiler's test harness is not enough if the two could differ. *Exit:* the `replay`, `certificate-at-office`, and `operator-blind` gates pass; the 16 scenarios produce identical answers through `charter test` and through `charter-server replay`; `test/server/` fixtures pin the answers.

**Phase 4, toolchain.** The managed `prove` toolchain, `--out json` per stage, `fmt`, `lsp` with hover and go-to-definition, `init` with UAT, `import`, ITF traces, `test --explore`, `render`, the EVM guard UAT (the guard is the evaluator on-chain against the artifact, §3a), `editors/vscode`. *Exit:* `uat/` scenarios for a fresh project through `prove` pass on macOS and Linux from a downloaded binary with no Lean installed; the PSA guard deploys and a scenario runs through it; a `charter-server` fed the same scenario gives the same answers.

**Phase 5, reference and release.** Spec chapters complete with conformance tests; `skills/`; examples dashboard; release pipeline producing signed binaries for macOS arm64, Linux x86_64/aarch64; v1.0 tag. *Exit:* a third program written by someone other than Eric, from the spec alone, passes `check`, `test`, and `prove`.
