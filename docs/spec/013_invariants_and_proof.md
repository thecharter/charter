# 013 — Invariants and proof

**Status:** draft (2026-10-23). Meaning fixed by plan §2.2.7, D8, D9, D10; wording awaits Eric. Implementation: 13.1–13.2 compliant (Phase 2's sixth slice); 13.3 *checked* and *decided* in use; 13.4 as the maintainer tool of Phase 2, the checkpointed chain (the managed toolchain is Phase 4); 13.5 pending.

**13.1 Invariants are checked.** `Invariant name When e` is a fact over no components that holds when `e` does (004.9). After every phrase, every invariant that does not hold is reported as a violation; `?name()` asks whether it holds. `test/spec/spec_013_1_invariant_checked.eflint`

**13.2 Exploration.** `charter test --explore N`, or the directive `//! explore: N` in a file, searches from the program's end state and from each scenario's end state: breadth-first over every enabled act instance (lawful behaviour; acts that are not enabled are not explored), up to `N` steps and a bound on distinct states, and reports the shortest trace after which some invariant does not hold as a failed claim naming the invariant and the acts. The search is deterministic: candidates are taken in declaration order, so the same program and depth always give the same trace. A search that finds nothing within its bound is a passing claim and says how many states it visited. An act whose domain is not enumerable (D15, 005.5) has no candidates of its own: the test file names them per component type with `//! explore-domain: <type> = v, a..b, "s"` (or `--explore-domain "<type> = …"`), a search bound and never a line of the institution. Without a menu for some component the search tries the values of that kind that occur in the state (the named heuristic *state-values*, reported in the output), reports the act as **unexplored**, and makes no passing claim: in test mode that report is a failed claim. `test/spec/spec_013_2_explore_finds_shortest.eflint`, `spec_013_2b_explore_safe.eflint`, `spec_013_2c_explore_lawful_only.eflint`, `spec_013_2d_explore_menu.eflint`, `spec_013_2e_explore_without_menu_is_not_a_pass.eflint`

**13.3 Tags (Law 10).** Every claim the tool prints carries one of *proved*, *decided*, *checked*, *assumed* and never a fifth. Every claim of `run`, `test`, and `check` is *checked*: the evaluator judged it at run time. Every claim of `prove` is *decided*: the kernel evaluated it on the program's concrete inputs, and it depends on no axiom. *Proved* (for all traces and parameters) arrives with the module theorems of 13.5.

**13.4 `charter prove` (D9).** A generator, not a mode: `charter prove <file.eflint>` writes a project under `.charter/prove/<program>/` containing the program's phrases **as data** (never as text), runs the checker on it under a memory cap and a time cap (`--memory MB`, default 6144; `--time S`, default 300), and reports one *decided* claim per theorem through the diagnostic channel; the author sees the claim's text and verdict, never the engine (`--show-checker` shows it). The project is a **checkpointed chain** (ruled 2026-10-25): the record after every phrase (`Prove.Summary`: the configuration, the verdicts so far, the invariants found violated) is embedded as data, as the compiled evaluator produced it, and one kernel theorem per phrase, `step_k : stepSummary S_{k-1} p_k = S_k`, asks the kernel to recompute that phrase alone, so the memory a decision needs is bounded by one phrase's evaluation whatever the program's length. Each step theorem is also the **Law 9 check** for its phrase: if the kernel computes anything else, that theorem fails and the report names the phrase's line. A scenario is a sub-chain forked from the record at its point, its end state checked for invariants (`viol_k`) and the configuration restored (`Prove.foldl_scenario`); the program's end state is checked last. The chaining lemmas (`Prove.foldl_phrase`, `foldl_scenario`, `foldl_step`) are general statements proved once in `Charter.Prove.Run` by rewriting alone (no `simp`, whose closing lemma carries `propext`); the generated proof of `summarize items = S_fin` only rewrites with them, and from it `program_decided` (`Prove.summary`: every claim's verdict in order, and every invariant that does not hold at the program's end state or at a scenario's, the states 13.2 searches from) and one theorem per claim and per invariant are read off, so a claim the evaluator already reported false fails at its own theorem with the note that the kernel agrees. The step theorems are closed by `kernel_rfl` (`Charter.Prove.Kernel`): `Eq.refl` handed to the kernel alone, as `decide +kernel` hands over its decision, with no `DecidableEq` instance (Lean cannot derive one for the nested inductives a configuration carries) and no elaborator comparison. A theorem counts as decided only if it depends on no axiom (Law 10); `tools/prove-check` also fails the battery on any `#print axioms` line naming one. The tags are unchanged: every per-claim theorem is about concrete inputs, *decided*; the chaining lemmas are plumbing proved once. Until the managed toolchain lands (Phase 4) this is a maintainer tool run inside the repository with its own toolchain. `test/prove/three_phrase.eflint` (one false claim, reported failed), `test/prove/module_use.eflint` (a `lib/` module's five invariants and a claim), `test/prove/scenario.eflint` (a scenario's sub-chain, its end state, the restored configuration); `tools/prove-check` runs them in the battery.

The chain is written as **modules of `--chunk` phrases** (default 5; a scenario's sub-chain may span modules), each importing the one before and each run as its own checker process, because the checker's resident size grows with every declaration it has elaborated and is not given back between them (measured 2026-10-25: about 30 MB per second of kernel work, monotone through a whole file, 10 GB for the 145-phrase `sortition_court` test in one process; in modules of 10 phrases the same test decides under the default cap at 4.7 GB, the resident size resetting at every module, its phrases costing about 400 MB each inside a module); per process the bound is a module's, whatever the program's length. The time cap is the whole run's, the memory cap each process's. *Open, for a measured program:* the modules could run in parallel if each carried its own copy of the record it starts from (today each imports the one before); and a cache keyed by the hash of `(S_{k-1}, p_k)` would spare an unchanged prefix when iterating on a long program. *Reopen condition for the per-phrase cost* (interning type names to `Nat`, recomputing strata only on declaration phrases): a single phrase that exceeds the cap on its own, which the chain's per-phrase failure will name; not before.

*Finding (2026-10-23), for the design of `prove`:* `Charter.Prove.Run` gives the evaluator as a pure function, and a *decided* claim would be `theorem t : (runText src).ok = true := by decide`. Measured on a three-phrase program (`Fact x Identified by A. +x(A). ?x(A).`), the kernel ran for ten minutes and was then killed out of memory, with no answer; the compiled evaluator answers the same question in a third of a second. The cause is representation: type names are `String`s (a `List Char` to the kernel), states are association lists compared structurally, and every step runs a fuel-indexed nondeterministic monad. `prove` therefore needs a kernel-oriented Core before it can discharge anything: names interned to `Nat` at resolution, states as sorted arrays keyed by those numbers, and the evaluator proved equal to a kernel-friendly evaluator rather than run in the kernel itself (plan §3: "the evaluator is the proved artifact"). This is Phase 2's open item and is not shipped as a `prove` that cannot discharge.

*Finding (2026-10-24), the cause located:* the evaluator's mutual block (`Charter.M.eval` and its fifteen companions) had been compiled by well-founded recursion, which the kernel never unfolds, because `foreach`/`scope` were polymorphic in their result type; and the parser was being run in the kernel too. With the binding loop moved out of the block (`scopeWith`/`foreachWith`) the block is structural on its fuel, and measured through `tools/kernel-probe`: parsing the three-phrase text alone exceeds 180 s (so the generator must embed parsed items, never text); resolving a declaration decides in 0.2 s; the whole three-phrase program, from parsed items, decides in about 200 s. That is the first kernel decision of a Charter program. The remaining cost is in the create phrase's evaluation and is the next thing to locate, one capped probe at a time.

*Finding (2026-10-24, late), the remaining cost located:* it was never in the kernel. Bisected one capped probe at a time: evaluating the compiled create term decides in a second at fuel 40 and at the real fuel of 100000 alike; so does `evalEffect`, and so does `Store.unions` over its result; but `semPhrase` on the same phrase passed 6 GB in 6 s under plain `by decide`, and still did at fuel 1. The same claim with `decide +kernel` decides in under a second, and so does the whole three-phrase program, which plain `decide` had taken about 200 s over. Plain `decide` first evaluates the `Decidable` instance in the elaborator (`Meta.whnf`), and that evaluation, not the kernel's, is what explodes on `semPhrase`; `decide +kernel` hands the closed term to the kernel directly, which decides it at once. Consequences: `prove`'s generator emits `decide +kernel`; interning names to `Nat` is no longer needed for this program and is deferred until a measured program needs it; the checked-in probe is `tools/probes/three_phrase_decides.lean`, run only through `tools/kernel-probe`.

*Finding (2026-10-25), the chain measured:* every `lib/` test decides under the default cap (`charter prove --show-checker`, one at a time): `entity_group` (70 phrases, 40 theorems) in 68 s at 2.7 GB, `exit_and_voice` (92, 52) 155 s, `oracle_feed` (52, 45) 183 s, `attested_lease` (73, 50) 187 s at 5.7 GB, `circuit_breaker` (68, 41) 274 s, `collateral_pool` (89, 59) 478 s, `residual_ledger` (87, 66) 573 s, all in one process before the module split; `sortition_court` (145, 70) needed the split (above). Before the chain, the entity-group test's genesis prefix plus one scenario was killed at 12.5 GB. The per-phrase cost is unchanged (about a second and 230 MB of kernel work per phrase of a library program; several seconds and 400 MB for the sortition test's); the chain bounds what any one process holds of it.

*Finding (2026-10-24, night), the generator measured:* with `decide +kernel` and the phrases embedded as data, `test/prove/three_phrase.eflint` decides in under a second and `test/prove/module_use.eflint` (a 40-type module instantiated, a conserving genesis, six theorems) in about two seconds at 1.8 GB resident. Three more things had to give before the kernel would decide anything: `Phrase.claimCount` recursed through `List Phrase` and had been compiled by well-founded recursion (`@[irreducible]`), which stalls the kernel the same way the evaluator's block had; it is now a mutual structural block. `String.foldl` (in `showString`) and `String.toLower` (in two resolver messages) carry `propext` in their termination proofs, so every decided theorem depended on an axiom; both are replaced (a fold over the character list; the kind's lower-case name spelled out) and `Prove.summary` depends on no axiom. The limit found: **the kernel's memory grows with its running time, about 230 MB per second of work** (its caches live for the whole declaration), at about a second per phrase of a `lib/` program: the genesis prefix of `test/lib/entity_group_test.eflint` (19 phrases) decides in 21 s at 4.9 GB; that prefix plus its first scenario passed 12.5 GB at 51 s and was killed; the whole file (about 70 phrases) is out of reach under any cap this machine allows. Two ways forward, for ruling: (a) a *checkpointed chain*, the generator writing the configuration after every phrase as data and one small theorem per phrase (`runPhrase cfg_k p_k = (cfg_{k+1}, outs_k)`), each a bounded kernel decision, joined by a chaining lemma proved once in `Prove.Run`; (b) cutting the per-phrase cost itself, first by interning type names to `Nat` (every lookup compares `String`s character by character in the kernel), then by recomputing strata only when the declarations change. (a) bounds memory for any program length; (b) only scales the constant. Phase 3's PSA (61 clauses, 16 scenarios) needs (a).

**13.5 Module properties (D8).** A standard-library module's properties are `Invariant`s in its `.charter` file (015.5; all eight modules, `lib/`), checked today and to be proved in `lib/lean/` by name and reported as *proved* when a program `Use`s the module (pending `prove`). Frame properties, that an act leaves a fact unchanged, are properties of acts and are not `Invariant`s; they wait for `prove` too.

*Differences from eFLINT:* eFLINT checks invariants after every phrase (13.1 is unchanged); exploration is Charter's, after Quint's `run` simulations.
